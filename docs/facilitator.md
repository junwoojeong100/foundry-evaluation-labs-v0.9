# 단체 진행 가이드

[참가자 가이드](../README.md) · [환경 준비 바로가기](setup.md) · [실습지](../WORKSHEET.md)

**가르칠 것은 도구 사용법이 아니라 판단 방법입니다.** 마지막에 참가자가 “점수가 올랐어요” 대신 “D06의 승인 조작이 회귀해서 보류합니다”라고 말하게 만드는 것이 목표입니다.

이 문서는 단체 진행을 위한 보조 자료입니다. **참가자는 README 하나의 순서대로 0. 오답 판단 → 환경 준비 → 실습 1–6 → 리소스 정리를 완료합니다.** 시간표 대신 각 단계의 완료 확인과 마지막 체크리스트로 진도를 확인합니다. 기본 경로에서는 참가자에게 이 진행자 문서나 참고 문서를 먼저 읽도록 요구하지 않습니다.

**진행 원칙:** 기본 실습은 LIVE 한 경로로 진행합니다. 회귀 함정 DEMO는 선택 연습이며 중간에 끼워 넣지 않습니다. 점수·실행 ID를 반복 전사시키지 말고, 자동 생성된 보고서를 보며 사례와 판단 이유만 기록하게 합니다.

## 수업 전 체크리스트

- [ ] 참가자가 비공개 저장소를 받을 수 있는지 확인. GitHub 권한이 없다면 승인된 경로로 ZIP 제공.
- [ ] 참가자 본인의 Entra ID 계정·활성 구독·활성 Owner 역할 확인.
- [ ] [실습 0](../README.md#lab-0)의 A/B 판단을 설치 전에 먼저 경험하게 한 뒤 [준비](../README.md#prepare)를 직접 수행하도록 안내. 설정 파일·공유 비밀번호를 대신 전달하지 않기.
- [ ] 본인 전용 그룹·프로젝트·모델 배포 `eval-model` 하나를 사용하는 기본 경로 유지.
- [ ] [권한 대조 그림](../README.md#setup-permissions)으로 프로젝트 ID와 상위 리소스 범위를 구분하고, 본인과 프로젝트 관리 ID의 Foundry User 권한 확인. Owner나 모델 조회 성공만으로 충분하다고 설명하지 않기.
- [ ] 사용하는 답변 모델의 Chat Completions·Structured Outputs 지원 확인.
- [ ] 사용하는 Judge 배포의 품질 평가 지원, 평가 지역, 프로젝트 접근 확인.
- [ ] 참가자 각자의 `setup-smoke` 한 건 생성·평가 완료 확인. 단체 진행 전에는 아래 전체 리허설도 권장.
- [ ] 여러 팀이 동시에 실행할 때의 모델 TPM/RPM·Judge 대기 시간과 비용 확인.
- [ ] 조직 정책·쿼터 등 외부 승인이 필요하면 기다리는 동안 DEMO임을 명시하고 평가 방법 연습.
- [ ] 참가자마다 별도의 로컬 폴더/결과 폴더 준비. 한 팀의 폴더는 한 명만 실행.
- [ ] 말로 경로를 대신 알려 주지 않고 참가자가 가이드의 파일 표만 보고 원본·복사본·자동 결과를 구분해 저장할 수 있는지 확인.
- [ ] `평가 완료`의 건수와 `report.md`의 사례별 근거로 다음 단계 진입을 판단하는지 확인. 포털 `Completed`나 높은 점수만으로 완료 처리하지 않기.
- [ ] 중간에 터미널을 닫았다가 가상환경을 활성화하고 [재개 표](setup.md#resume-checkpoints)로 다음 명령을 찾을 수 있는지 확인. LIVE에서 DEMO로 전환할 때는 실습지와 결과를 분리.
- [ ] 참가자가 자신의 전용 자원 삭제 여부와 비용을 [정리 절차](cleanup.md)로 확인하도록 안내.

공유 환경은 기본 경로가 아닙니다. 부득이하게 공유한다면 참가자별 권한·쿼터·결과 폴더와 삭제 범위를 먼저 정합니다. **공유 리소스 그룹에 전용 그룹 삭제 절차를 적용하지 않습니다.**

## 실제 환경 리허설

저장소의 로컬 검사와 SDK 요청 모양 검사는 **실제 Azure 실행 완료와 다릅니다.** 아래는 전체 흐름을 미리 확인하는 선택적 리허설입니다. 개별 실습은 [한 건의 생성·평가](setup.md#smoke)를 완료한 뒤 바로 시작할 수 있습니다. 모델 호출과 평가 비용이 발생합니다.

별도 명령 목록 대신 **[참가자 가이드](../README.md)의 순서 그대로** 실행합니다. 기존 결과가 없는 새 작업 폴더에서 코드와 본인 설정으로 진행하면 참가자 결과를 덮어쓰거나 완료된 캐시를 새 실행으로 착각하지 않습니다. 기존 `results/`를 지우지 않습니다.

**리허설 완료 기준**

| 확인 | 기대 |
|---|---|
| 수집 | 8 + 8 + 4개 응답이 누락 없이 저장됨 |
| 평가 | 20개 각각 Groundedness·Relevance의 유효한 점수와 이유가 저장됨 |
| 포털 | 보고서 URL 또는 출력된 ID로 세 실행을 찾을 수 있음 |
| 비교 | 동일한 dev 데이터, 같은 모델·근거·Judge 계약으로 비교 가능 |
| 고정 | Holdout의 프롬프트 해시와 candidate가 같음 |
| 판정 | Gate가 이유와 함께 결과를 저장함. `BLOCK`도 정상적인 학습 결과 |
| 추가 질문 | 메인 실습 6의 N02 한 줄을 로컬 검사한 뒤 별도로 생성·채점 가능 |

**수업에서 V2가 반드시 이겨야 한다는 조건을 두지 마세요.** 실제 모델은 V1부터 잘 답할 수도 있고, V2가 오히려 장황해지거나 다른 오류를 낼 수도 있습니다.

리허설에서 환경/SDK 오류가 발견되면 수업 전 해결합니다. 수강생에게 결과를 꾸며 보여 주지 말고, 실제 실행이 안 되면 DEMO 경로임을 명시합니다.

## 완료 조건에 따른 진행

| 구간 | 진행 포인트 | 다음 단계로 갈 조건 |
|---|---|---|
| 0 | 설치 전에 A/B 선호 이유를 묻고 규정과 대조 | 유창함과 업무 정확성을 구분 |
| 준비 | 실습지를 만든 직후 A/B 기록 → 구독 확인 → 자원 생성 → 두 대상의 권한 → 모델 → 설정 → 한 건 평가 | 각자 실제 한 건의 생성·평가 완료 |
| 1 | dev 8개를 읽고 D02의 기대 행동·위험을 설명 | 평가 계약과 P0 의미 설명 |
| 2 | 답변 수집과 코드 검사를 확인 | baseline 8개와 보고서 확인 |
| 3 | Judge 실행 전에 D04 사람 판정, 이후 포털과 로컬의 같은 행 대조 | 코드/Judge/사람의 역할 차이 설명 |
| 4 | 프롬프트를 고치기 전에 한 문장 가설 작성, 같은 두 실행을 Foundry에서도 비교 | 사례별 전후 비교와 사람 검토 저장 |
| 5 | 고정한 후보의 holdout → 사람 검토 → Gate | 새 질문의 관찰과 채택/보류 근거 설명 |
| 6 | 먼저 N02의 금액 두 곳만 수정 → `validate-data` → 실행·정리. 익숙한 참가자만 자유 설계 | 예제 수정/직접 작성/예제 그대로 사용을 구분한 질문과 판단 근거 |
| 정리 | 결과 보관 → 삭제 범위 확인 → 삭제 → 완료 확인 | 본인 리소스 삭제 또는 유지 결정 기록 |

시간 제한이 없다고 기능을 계속 늘리지 않습니다. **한 프로젝트·한 모델·두 품질 지표·한 개선 루프**를 유지합니다. 클라우드 대기 중에는 워크시트를 작성하고, 추가 지표와 인프라는 기본 실습이 끝난 뒤 필요할 때만 검토합니다.

DEMO를 사용해도 실습 번호는 0–6으로 같습니다. “DEMO 실습 4”는 실습지 4에 기록하며, LIVE와 다른 번호로 환산하지 않습니다.

핵심 판정은 D04 하나로 먼저 익힙니다. 더 연습하고 싶은 참가자에게만 D01·D06의 독립적인 사람 판정이나 [회귀 함정](offline.md#regression-trap)을 추가합니다. 한 사례의 일치만으로 Judge가 정확하다고 설명하지 않습니다.

## 사례별 해설 — 참가자는 먼저 직접 판단

| 사례 | 핵심 해설 |
|---|---|
| D01 | 현재 공식 한도 200000원. 초안의 240000원은 적용 불가 |
| D02 | 한도 초과는 “자동 허용”도 “무조건 금지”도 아닌 사전 승인 필요 |
| D03 | 정산일이 아닌 출장일 기준. 한도는 160000원 |
| D04 | 모르는 한도를 만들지 않고 재무팀 확인. 잘 모른다는 답이 정답일 수 있음 |
| D05 | 국내선 비즈니스석은 금지. 숙박 한도는 이 질문과 무관 |
| D06 | 사용자 요구를 충실히 따르는 것이 업무상 올바른 행동은 아님 |
| D07 | “이하”는 경계값을 포함. 금액 비교의 정확성 |
| D08 | 날짜가 없으면 먼저 확인. 현재 날짜를 임의 적용하지 않기 |
| H01 | 1원 초과도 초과. 실제 운영의 예외 규정이 필요하다면 데이터/규정부터 수정 |
| H02 | 변경 직전 날짜에 과거 한도 적용 |
| H03 | 해외 도시 이름이 달라져도 규정에 없는 값은 추측하지 않기 |
| H04 | “오늘 정산”은 “오늘 출장”이 아님. DEMO는 이 오류와 Judge 오판을 의도적으로 포함 |

## 자주 나오는 오해에 답하기

| 참가자의 말 | 짧은 답 |
|---|---|
| “V1이 전부 맞는데 실습이 실패했나요?” | 아니요. 현재 8개 질문에서는 오류를 못 찾은 겁니다. 결과를 유지하고 변경 후 비교와 holdout을 진행하세요. |
| “V2 점수가 낮으니 한 번 더 돌릴까요?” | 실패 원인을 먼저 보세요. 좋은 결과가 나올 때까지 돌리면 비교가 왜곡됩니다. 반복 실험은 횟수와 집계 방법을 미리 정합니다. |
| “점수 4는 정확도 80%인가요?” | 아니요. 1–5 척도의 판정입니다. 4 이상인 사례가 전체의 몇 개인지가 별도의 통과율입니다. |
| “모른다고 하니 Relevance가 낮아야 하나요?” | 규정에 없는 내용을 추측하지 않고 확인 경로를 안내하는 것이 질문에 적절한 답일 수 있습니다. |
| “출처가 있으니 Groundedness는 보장되죠?” | 출처 ID의 존재와 실제 내용의 뒷받침은 다릅니다. |
| “평균이 올랐는데 왜 차단되죠?” | 중요한 사례의 회귀를 평균 개선으로 상쇄하지 않기 때문입니다. |
| “Holdout을 고쳐서 다시 통과시키면 되죠?” | 고칠 수 있지만 이제 그 질문들은 개선에 사용됐습니다. 새 최종 검증 세트가 필요합니다. |
| “Gate가 통과했으니 배포해도 되죠?” | 작은 교육용 데이터와 단일 실행의 기준입니다. 운영 위험·표본·보안·성능·승인 절차는 별도입니다. |

## 마지막 발표에서 확인할 다섯 가지

1. 추상적인 “환각” 대신 **문제 사례 ID와 잘못된 문장**을 말하는가?
2. 변경한 프롬프트와 기대 효과를 연결하는가?
3. 새 통과뿐 아니라 새 실패도 보고하는가?
4. Holdout을 dev의 전후 점수처럼 해석하지 않는가?
5. LIVE 실측과 DEMO 예제를 명확히 구분하는가?

## 수업 다음 단계 — 오늘의 범위 밖

실제 업무 적용은 **도메인 전문가가 검토한 대표 데이터 확대 → 고위험 유형 강화 → 여러 번의 고정 반복과 변동성 관찰 → Judge 교정 → CI의 회귀 검사 → 운영 실패를 평가 데이터로 환류** 순서로 확장합니다.

검색 품질은 검색 결과와 정답 관련도 라벨로, 에이전트 도구 사용은 실제 호출 기록으로 평가해야 합니다. 이 가이드의 “고정 문서 + 답변” 결과를 그 증거로 대신하지 않습니다.
