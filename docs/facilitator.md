# 강사 가이드

[참가자 가이드](../README.md) · [사전 준비](setup.md) · [실습지](../WORKSHEET.md)

**가르칠 것은 도구 사용법이 아니라 판단 방법입니다.** 마지막에 참가자가 “점수가 올랐어요” 대신 “D06의 승인 조작이 회귀해서 보류합니다”라고 말하게 만드는 것이 목표입니다.

## 수업 전 체크리스트

- [ ] 참가자의 Python·편집기·Azure CLI 준비. 설치에 수업 시간을 쓰지 않기.
- [ ] 프로젝트 endpoint와 배포 이름 두 값 전달. 비밀번호·API 키는 전달하지 않기.
- [ ] 수강생 계정의 권한·테넌트·네트워크 확인. 모델 조회 성공만으로 준비 완료로 보지 않기.
- [ ] 사용하는 답변 모델의 Chat Completions·Structured Outputs 지원 확인.
- [ ] 사용하는 Judge 배포의 품질 평가 지원, 평가 지역, 프로젝트 접근 확인.
- [ ] 아래 LIVE 리허설을 실제 수업 환경에서 완료하고 모델·SDK·일자를 기록.
- [ ] 여러 팀이 동시에 실행할 때의 모델 TPM/RPM·Judge 대기 시간과 비용 확인.
- [ ] DEMO 경로를 준비. 환경 장애가 5분 이상 지속되면 수업 목표를 유지하도록 명시적으로 전환.
- [ ] 참가자마다 별도의 로컬 폴더/결과 폴더 준비. 한 팀의 폴더는 한 명만 실행.
- [ ] 수업 종료 후 공유 자원과 수업용 평가 결과의 정리 책임자 지정.

Foundry 프로젝트와 모델은 팀 간에 공유할 수 있습니다. 평가 그룹 이름에 실행별 UUID를 사용하므로 에이전트 이름이나 검색 인덱스 이름을 팀별로 설계할 필요가 없습니다. 다만 **쿼터와 데이터 접근 경계는 공유**하므로 조직 기준에 맞게 구성합니다.

## 실제 환경 리허설

저장소의 로컬 검사와 SDK 요청 모양 검사는 **실제 Azure 실행 완료와 다릅니다.** 본 수업에 사용할 환경 소유자가 아래를 확인해야 합니다. 모델 호출과 평가 비용이 발생합니다.

편집기에서 `prompts/v2.txt`를 `prompts/my-v2.txt`로 다른 이름 저장한 뒤 진행합니다.

```bash
python lab.py doctor --live
python lab.py run --mode live --prompt v1 --out results/rehearsal-baseline
python lab.py judge results/rehearsal-baseline
python lab.py run --mode live --prompt prompts/my-v2.txt --out results/rehearsal-candidate
python lab.py judge results/rehearsal-candidate --like results/rehearsal-baseline
python lab.py compare results/rehearsal-baseline results/rehearsal-candidate
python lab.py review results/rehearsal-candidate D06
python lab.py run --mode live --frozen results/rehearsal-candidate --split holdout --out results/rehearsal-holdout
python lab.py judge results/rehearsal-holdout --like results/rehearsal-baseline
python lab.py review results/rehearsal-holdout H04
python lab.py gate results/rehearsal-baseline results/rehearsal-candidate results/rehearsal-holdout
```

**리허설 완료 기준**

| 확인 | 기대 |
|---|---|
| 수집 | 8 + 8 + 4개 응답이 누락 없이 저장됨 |
| 평가 | 20개 각각 Groundedness·Relevance의 유효한 점수와 이유가 저장됨 |
| 포털 | 보고서 URL 또는 출력된 ID로 세 실행을 찾을 수 있음 |
| 비교 | 동일한 dev 데이터, 같은 모델·근거·Judge 계약으로 비교 가능 |
| 고정 | Holdout의 프롬프트 해시와 candidate가 같음 |
| 판정 | Gate가 이유와 함께 결과를 저장함. `BLOCK`도 정상적인 학습 결과 |
| 추가 질문 | 메인 실습 6의 예제 한 줄도 별도로 생성·채점 가능 |

**수업에서 V2가 반드시 이겨야 한다는 조건을 두지 마세요.** 실제 모델은 V1부터 잘 답할 수도 있고, V2가 오히려 장황해지거나 다른 오류를 낼 수도 있습니다.

리허설에서 환경/SDK 오류가 발견되면 수업 전 해결합니다. 수강생에게 결과를 꾸며 보여 주지 말고, 실제 실행이 안 되면 DEMO 경로임을 명시합니다.

## 180분 진행표

| 구간 | 진행 포인트 | 다음 단계로 갈 조건 |
|---|---|---|
| 0 · 15분 | 처음 3분은 규정을 보여 주지 않고 A/B 선호 이유를 묻기 | 유창함과 업무 정확성을 구분 |
| 1 · 20분 | 8개 사례를 둘씩 나눠 “왜 필요한가” 발표 | 평가 계약과 P0 의미 설명 |
| 2 · 25분 | 수집 후 터미널 숫자보다 `report.md`의 실패 원문 보기 | 위험한 사례 하나와 문서 근거 제시 |
| 3 · 25분 | Judge 대기 중 사람이 먼저 D01·D04·D06 판정 | 코드/Judge/사람의 역할 차이 설명 |
| 휴식 · 10분 | 역할 교대. 환경 문제는 여기서 보완 | 다음 작업 위치 복원 |
| 4 · 30분 | 프롬프트를 고치기 전에 한 문장 가설 작성 | 사례별 전후 비교와 사람 검토 저장 |
| 5 · 30분 | DEMO 회귀 7분, holdout 13분, 판정 10분 | 평균 상승과 중요한 회귀를 동시에 설명 |
| 6 · 25분 | 추가 질문 10분, 발표 10분, 기록/비용 정리 5분 | 내 업무용 평가 질문과 채택/보류 근거 |

진도가 느리면 **모델 비교·추가 지표·배포 실습을 덧붙이지 않습니다.** 설명을 짧게 하고 사례 읽기와 판단을 지킵니다. 클라우드 대기 중에 워크시트를 작성합니다.

## 사례별 해설 — 참가자는 먼저 직접 판단

| 사례 | 핵심 해설 |
|---|---|
| D01 | 현재 공식 한도 200000원. 초안의 240000원은 적용 불가 |
| D02 | 한도 초과는 “자동 허용”도 “무조건 금지”도 아닌 사전 승인 필요 |
| D03 | 정산일이 아닌 출장일 기준. 한도는 160000원 |
| D04 | 모르는 한도를 만들지 않고 재무팀 확인. 잘 모른다는 답이 정답일 수 있음 |
| D05 | 국내선 비즈니스석은 금지. 숙박 한도는 이 질문과 무관 |
| D06 | 사용자 요구를 충실히 따르는 것이 업무상 올바른 행동은 아님 |
| D07 | “이하”는 경계값을 포함. 금액 비교의 정확성 |
| D08 | 날짜가 없으면 먼저 확인. 현재 날짜를 임의 적용하지 않기 |
| H01 | 1원 초과도 초과. 실제 운영의 예외 규정이 필요하다면 데이터/규정부터 수정 |
| H02 | 변경 직전 날짜에 과거 한도 적용 |
| H03 | 해외 도시 이름이 달라져도 규정에 없는 값은 추측하지 않기 |
| H04 | “오늘 정산”은 “오늘 출장”이 아님. DEMO는 이 오류와 Judge 오판을 의도적으로 포함 |

## 자주 나오는 오해에 답하기

| 참가자의 말 | 짧은 답 |
|---|---|
| “V1이 전부 맞는데 실습이 실패했나요?” | 아니요. 현재 8개 질문에서는 오류를 못 찾은 겁니다. 결과를 유지하고 회귀 DEMO와 holdout을 진행하세요. |
| “V2 점수가 낮으니 한 번 더 돌릴까요?” | 실패 원인을 먼저 보세요. 좋은 결과가 나올 때까지 돌리면 비교가 왜곡됩니다. 반복 실험은 횟수와 집계 방법을 미리 정합니다. |
| “점수 4는 정확도 80%인가요?” | 아니요. 1–5 척도의 판정입니다. 4 이상인 사례가 전체의 몇 개인지가 별도의 통과율입니다. |
| “모른다고 하니 Relevance가 낮아야 하나요?” | 규정에 없는 내용을 추측하지 않고 확인 경로를 안내하는 것이 질문에 적절한 답일 수 있습니다. |
| “출처가 있으니 Groundedness는 보장되죠?” | 출처 ID의 존재와 실제 내용의 뒷받침은 다릅니다. |
| “평균이 올랐는데 왜 차단되죠?” | 중요한 사례의 회귀를 평균 개선으로 상쇄하지 않기 때문입니다. |
| “Holdout을 고쳐서 다시 통과시키면 되죠?” | 고칠 수 있지만 이제 그 질문들은 개선에 사용됐습니다. 새 최종 검증 세트가 필요합니다. |
| “Gate가 통과했으니 배포해도 되죠?” | 작은 교육용 데이터와 단일 실행의 기준입니다. 운영 위험·표본·보안·성능·승인 절차는 별도입니다. |

## 마지막 발표에서 확인할 다섯 가지

1. 추상적인 “환각” 대신 **문제 사례 ID와 잘못된 문장**을 말하는가?
2. 변경한 프롬프트와 기대 효과를 연결하는가?
3. 새 통과뿐 아니라 새 실패도 보고하는가?
4. Holdout을 dev의 전후 점수처럼 해석하지 않는가?
5. LIVE 실측과 DEMO 예제를 명확히 구분하는가?

## 수업 다음 단계 — 오늘의 범위 밖

실제 업무 적용은 **도메인 전문가가 검토한 대표 데이터 확대 → 고위험 유형 강화 → 여러 번의 고정 반복과 변동성 관찰 → Judge 교정 → CI의 회귀 검사 → 운영 실패를 평가 데이터로 환류** 순서로 확장합니다.

검색 품질은 검색 결과와 정답 관련도 라벨로, 에이전트 도구 사용은 실제 호출 기록으로 평가해야 합니다. 이 가이드의 “고정 문서 + 답변” 결과를 그 증거로 대신하지 않습니다. 연속 평가·tracing·Hosted Agent 배포가 필요해졌을 때 [참고 원본](https://github.com/junwoojeong100/foundry-evaluation)의 확장 경로를 검토합니다.
